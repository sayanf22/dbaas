Summary of the current design (Rev 4.0):
  - Back to K3s, as in the original PDF. A cell = one K3s v1.36 cluster of 3 Linux VMs in ONE provider and
    ONE region on a private network: cp-1 (2 vCPU / 4 GB, control plane only) + node-1, node-2 (8 vCPU /
    24 GB / 200 GB NVMe, control plane + platform + tenants). 3 servers with embedded etcd; growth nodes
    join as agents. Oracle Cloud is no longer used.
  - Provider-neutral: no provider chosen yet. Any provider passing the VM checklist (plan/03 §2.1) within
    Rs 5,600/month for the cell; in practice the value-VPS class. Everything is built locally first (k3d).
  - A K3s server on a small VM with the rest on AWS/GCP is technically possible but not used: embedded etcd
    needs all servers on one private network, cross-cloud traffic is billed, a broken link freezes the
    cluster, and hyperscaler VMs cost 5-6x the budget. AWS/GCP can be separate cells later.
  - Budget: whole platform <= Rs 9,000/month (launch ~Rs 5,700-5,900; ~Rs 8,100-8,300 with Supabase Pro).
  - Plans: base 0.1 vCPU (burst 0.5) / 512 MiB / 5 GB Rs 299 + GST; plus 0.25 (1) / 1 GiB / 10 GB Rs 699;
    premium 0.5 (1) / 2 GiB / 20 GB Rs 1,399; 7-day PITR on every plan. A cell holds ~53 base tenants.
  - Networking: flannel wireguard-native (encrypted between nodes) + K3s's NetworkPolicy controller;
    only TCP 5432 is public; SSH and the K3s API only through Cloudflare Tunnel + Access.
  - Storage: TopoLVM on local NVMe; backups and etcd snapshots to Cloudflare R2.
  - Postgres ingress: pg-gateway (Rust) DaemonSet on hostPort 5432 on every tenant node; DNS has one
    A record per node (clients fail over) -> PgBouncer (pooled hostname) or Postgres (-direct hostname).
  - HTTP ingress: one Cloudflare Tunnel per cell; WAF, DDoS, Turnstile, Access; Next.js 16 static exports
    (public site, dashboards) on Workers Static Assets.
  - Admin/management layer: Supabase Free (ap-south-1) through the IPv4 Supavisor pooler, then Pro at ~30
    tenants = control-plane database + Supabase Auth. No customer data in Supabase.
  - Secrets: SOPS + age in git, decrypted by Flux; K3s secrets encryption at rest. Images in ghcr.io.
  - MCP: remote MCP server (Go SDK, spec 2026-07-28) + our own OAuth 2.1 server mcp-auth (CIMD, RFC 8707).
  - Languages: Rust for pg-gateway only; Go for control plane, operator, agent, MCP, CLI; TypeScript
    (Next.js) web; every backend component ships as a Docker-built multi-arch image.
  - Scaling: nodes added only when revenue covers them; cells of <= 50 nodes / <= 1,500 tenants.
  - Unchanged from the PDF: tenant model, invariants, MCP permission model. Acceptance gates keep the PDF's
    list and add Scale, Node loss, Cost and Billing gates and concrete Static-stability timings (plan/04 §8).

0. Executive architecture
The platform is a managed PostgreSQL service where each customer receives an independently managed 
PostgreSQL instance and database, while multiple tenant workloads can share the same physical VM/node. [Rev 4.0] A K3s cluster 
is the shared scheduler and control layer; the PostgreSQL Pod is the tenant resource boundary. The control 
plane remains outside the customer data plane.
Figure 1. End-to-end control-plane and data-plane architecture.
Core invariant
Never attempt to distribute ordinary writes for one PostgreSQL database by round-robin routing across 
providers. Horizontal write scale is achieved by assigning different tenants to different clusters and migrating 
tenants between them.

1. Product contract and terminology
1.1 Tenant, customer and user
A customer organization is a tenant of the DBaaS. An organization may contain multiple human users and 
service identities. Each tenant owns one PostgreSQL database resource and one PostgreSQL instance workload 
in the default architecture.
1.2 Database unit
The service unit presented to the customer is a PostgreSQL database with a stable logical hostname, 
credentials, storage entitlement, CPU entitlement, memory entitlement, backup policy and MCP permission 
policy.
1.3 Production promises
 Free/shared tiers are best-effort unless an HA contract is explicitly sold and tested.
 CPU and memory limits are enforced at the Pod/container level. PostgreSQL databases inside one process 
do not receive independent CPU/RAM cgroup limits.
 A dedicated VM or cluster is an isolation tier; a dedicated single VM is not HA.

2.2 Control-plane/data-plane separation
The control plane owns catalog state and desired infrastructure state. It never becomes a proxy for customer 
application data. The data plane owns PostgreSQL execution, storage and customer database contents. This 
separation limits blast radius and keeps the control database replaceable.

3.2 Why one PostgreSQL instance per tenant
PostgreSQL resource behavior is primarily instance-level. CloudNativePG explicitly recommends a single 
application-owned database per PostgreSQL cluster because resource management and physical PITR are 
simpler at the instance level. This makes the tenant instance the natural unit for Kubernetes CPU/RAM policy 
and recovery boundaries.
Boundary to remember
One database per tenant is a logical data boundary. One PostgreSQL Pod/instance per tenant is the compute 
and operational boundary. These are intentionally paired in this design.
4. Shared VM and K3s resource model
Figure 2. The K3s cluster is shared; PostgreSQL Pods carry tenant-specific compute policies.
4.1 What K3s is doing [Rev 4.0]
K3s runs the Kubernetes control plane on three of our VMs (embedded etcd, 3 servers); growth nodes
join as agents. We run what a managed service would: etcd snapshots to R2, upgrades with
system-upgrade-controller, evacuation for node retirement, and a capacity controller with a budget
guard [Rev 4.0]. One K3s cluster schedules and manages many tenant Pods on the 
same VM or node pool. It is not installed inside each tenant allocation. It is the shared orchestration layer.

4.3 Capacity calculation
Placement is based on requested resources plus measured PostgreSQL overhead and node reserve, not simply 
on the sum of plan labels. Reserve capacity for kubelet/K3s system reservations (use node Allocatable), the OS, CloudNativePG, poolers, monitoring, filesystem 
cache, WAL bursts, backup jobs and recovery operations.
AVAILABLE_CAPACITY = NODE_CAPACITY - SYSTEM_RESERVE - PLATFORM_RESERVE - SAFETY_HEADROOM
ADMISSION = requested_cpu <= available_cpu AND requested_memory <= available_memory
PLACEMENT = eligible cluster with sufficient capacity + policy compatibility
4.4 Shared-node limitation
CPU and memory limits do not make the shared VM a separate physical failure domain per tenant. Tenants still 
share the host kernel, disk device, network interface and VM failure domain. Storage IOPS isolation must be 
designed separately if it becomes a contractual requirement.

6.3 Migration networking rule
Route changes affect new connections. Existing PostgreSQL TCP sessions remain on the old path. The migration 
contract therefore includes connection draining, reconnect guidance and transaction retry behavior.
6.4 Cloudflare role
Cloudflare is used for HTTP control-plane traffic, DNS, TLS, WAF, DDoS protection, Access/Tunnel for 
administration. [Rev 3.2] All HTTP ingress uses Cloudflare Tunnel; staff tools sit behind Cloudflare Access;

the private K3s API and SSH use Cloudflare Tunnel + Access [Rev 4.0]. Postgres reaches tenants via DNS -> pg-gateway on the nodes. Cloudflare is not used as the raw 
arbitrary TCP PostgreSQL data path.

8. Reconciliation and job execution
8.1 Desired-state model
The API writes desired state. The controller observes actual state and reconciles toward the desired state. Long-
running infrastructure work is never performed synchronously inside the HTTP request handler.
REQUESTED -> AUTHORIZED -> QUEUED -> DISCOVERED -> CREATED/UPDATED -> POLLED -> VERIFIED -> 
SUCCEEDED
                         |
                         +-> RETRYABLE_FAILURE -> BACKOFF -> QUEUED
                         +-> PERMANENT_FAILURE -> FAILED
                         +-> AMBIGUOUS -> QUERY_PROVIDER_STATE -> RECONCILE
8.2 Job requirements
 Idempotency key and operation ID.
 Lease ownership and timeout.
 Retries with exponential backoff.
 Provider request ID when available.
 Progress events and structured logs.
 Cancellation only where the operation is safely cancellable.
 Explicit destructive states and manual intervention path.
 Complete audit history.
8.3 Initial queue choice
[Rev 3.1] Use River (Go job queue on the control database): jobs are inserted in the same transaction as the
desired-state change, which is the transactional outbox; River provides retries, uniqueness and leases. Add a 
more complex message system only when measured workload and operational requirements justify it.

11.3 Dedicated does not automatically mean HA
A dedicated single VM is isolated but still has a single failure domain. HA requires replication, 
fencing/promotion authority, redundant gateway capacity, independent backups and tested failover.
12. High availability
Figure 4. Paid HA and multi-provider recovery topology.
12.1 Paid HA tier
 At least two PostgreSQL data nodes for basic failover; three for stronger redundancy and repair capacity.
 Separate failure domains/topology spread where available.
 Two gateway replicas or an equivalent redundant front door.
 Fencing / promotion authority to prevent split brain.
 Independent backup target.
 Lag monitoring and automated health evaluation.
12.2 Kubernetes control-plane HA (K3s) [Rev 4.0]
Each cell runs an HA K3s topology: three server nodes for embedded-etcd quorum (cp-1, node-1, node-2) on one
private network, with etcd snapshots every 6 h to R2. Availability also comes from static stability (running
databases don't depend on the Kubernetes API or the control plane) and a second cell later. HA PostgreSQL
places instances on different nodes. The original K3s guidance still applies: use an HA K3s topology with 
three or more server nodes for embedded-etcd quorum. The cheapest single-node deployment is explicitly 
best-effort and not an HA service.
12.3 HA promise
Publish measured RPO/RTO only after destructive tests: kill the primary, isolate the primary, partition the 
network, lose a replica and validate that exactly one writable primary exists.

13.2 R2 as backup target [Rev 3.2: adopted]
Backups and WAL go to Cloudflare R2 (https://<account_id>.r2.cloudflarestorage.com), one bucket per cell and
one prefix per tenant, with AWS_REQUEST_CHECKSUM_CALCULATION / AWS_RESPONSE_CHECKSUM_VALIDATION = when_required
and AWS_DEFAULT_REGION=auto on the Barman plugin sidecar. WAL is compressed; base backups are uncompressed
because R2 rejects the uneven multipart parts compressed barman streams produce. One 8-day bucket lock (longer than
the weekly base interval) protects recent backups [Rev 3.3]. India-only customers can get an India S3-compatible target per tenant [Rev 4.0].
Original text (the release-gate rule still applies):
Cloudflare R2 is economically attractive and S3-compatible, but compatibility is not a substitute for testing. 
Treat the exact CloudNativePG/Barman Cloud Plugin/R2 combination as a release gate. Until it passes, maintain 
a verified canonical recovery target for higher-value tiers.
13.3 PITR
PITR is cluster/instance scoped. For a tenant restore request, restore the physical recovery target into a 
temporary recovery environment, validate the requested recovery point, extract or restore the tenant database 
into an isolated destination, verify roles/ACLs, then publish the route only after approval.
13.4 Logical tenant exports
Maintain periodic logical exports for portability, deletion recovery and tenant-level recovery workflows. 
Maintain a separate managed manifest for cluster-wide globals that are not fully represented by a normal 
pg_dump.
14. Tenant migration
14.1 Small tenant migration
1. Create destination PostgreSQL instance.
2. Apply compatible PostgreSQL version and extension set.
3. Create roles and schema.
4. Perform dump/restore or another supported migration method.
5. Validate rows, sequences, extensions, permissions and application connection.
6. Quiesce or otherwise control writes for final cutover.
7. Publish new route generation.
8. Drain old connections.
9. Verify customer connection and application writes.
10. Retain source until rollback window expires.
14.2 Hot tenant migration
For larger or hot tenants use logical replication where its semantics match the workload. Validate DDL, 
sequences, large objects, concurrent writes, replication lag, cutover and rollback explicitly because logical 
replication is not a complete physical clone mechanism.
14.3 Migration truth
Logical replication is a migration tool, not a zero-downtime guarantee. Existing TCP sessions do not migrate, 
and client reconnect behavior remains part of the product contract.

15. Multi-provider and disaster recovery
Providers are independent capacity domains. Register each provider/region as a separate cluster or VM pool. 
Never stretch one Kubernetes cluster across regions or providers over the ordinary public internet. [Rev 3.1]
Each K3s cell (one provider + region) is an independent capacity and failure domain [Rev 4.0].
15.1 Provider adapter contract
Capability Required metadata
Compute instance type, CPU, RAM, architecture, availability
Network private networking, routing, firewall/security rules
Storage disk type, capacity, IOPS characteristics, encryption
Cluster Kubernetes (K3s, or a managed Kubernetes for future cells) lifecycle and supported versions [Rev 4.0]
Database PostgreSQL image, extensions, CloudNativePG support
Backup object storage target and connectivity
Cost hourly cost, quotas, capacity constraints
Health provider and cluster health signals
15.2 DR modes
 Asynchronous replica for provider recovery
 WAL/PITR rebuild target
 Scheduled rebuild capacity
 Cross-provider tenant migration target
15.3 Promotion rule
Promotion is controlled: declare provider failure, fence or revoke the old writer, verify target recovery position 
and health, record expected RPO, promote exactly one target, switch logical routing, verify application writes, 
then rebuild the old site before rejoining it.

17.3 Agent execution loop
1. User sends natural-language instruction.
2. Agent determines which MCP tool is needed.
3. MCP gateway validates OAuth token, issuer, audience, tenant and scope.
4. Permission engine checks the exact operation and resource.
5. Risk policy determines whether confirmation or elevated approval is required.
6. Tool executor performs the operation using a constrained role/connection.
7. Result is validated and normalized.
8. Operation and audit event are recorded.

Agent action contract
The agent is expected to perform real database work, not merely explain SQL. Examples include creating 
tables, applying migrations, inserting or updating records, diagnosing performance, creating backups, 
restoring from a recovery point, or changing the tenant resource profile - but every action is executed 
through the same authenticated, permission-checked and audited path.
17.4 Interactive approvals
Destructive and privileged operations require explicit confirmation by default in interactive sessions. An 
approval is bound to the operation hash, tenant, database, actor, scope and expiry; changing any of those 
invalidates the approval.
18. AI database safety
18.1 SQL execution policy
 Do not expose an unrestricted superuser query tool to an AI agent.
 Separate read and write execution roles.
 Apply statement timeouts and lock timeouts.
 Bound result rows/bytes and execution time.
 Reject multi-statement execution unless a dedicated migration tool handles it.
 Reject unsafe functions, COPY and server-program/file access from general AI SQL tools.
 Use a SQL parser as one defense layer, never as the only security boundary.
 Treat database comments, row values, schema text, logs and query results as untrusted input because they 
may contain prompt-injection instructions.
18.2 Write operation model
inspect -> plan -> permission check -> risk classify -> optional backup
-> explicit approval (when required) -> execute -> verify -> audit -> report
18.3 Tool groups
 database: list/get/schema/query_read/query_write/migrate
 operations: create/get/cancel
 backup: create/list/restore
 scaling: cpu/memory/storage
 credentials: create/rotate/revoke
 admin: tenant/cluster/provider actions - platform staff only

20. Secrets and credential lifecycle
1. Generate credentials through the control plane/controller.
2. Store only the minimum necessary secret material.
3. Expose credentials only through authorized customer channels.
4. Create a new credential before revoking the old credential during rotation.
5. Update pooler/auth configuration and validate the new credential.
6. Switch the active credential.
7. Revoke the old credential after the grace period.
8. Record the rotation event without logging the secret.
For larger deployments, evaluate a dedicated secrets engine such as OpenBao/Vault for dynamic or short-lived 
credentials. Do not introduce it before the operational need justifies the added complexity.

26. PostgreSQL lifecycle and extensions
26.1 Version policy
 Pin a supported major version for shared pools.
 Allow premium/dedicated tenants to choose among the provider-supported majors only where automation 
supports it.
 Upgrade by tested rolling or new-cluster procedures.
 Never allow arbitrary server-level changes that bypass the controller/operator.
26.2 Extensions
Maintain an approved extension catalog per PostgreSQL major version and provider image. A tenant is eligible 
for a cluster only if its required extensions can be installed and recovered there.
26.3 Connection pooling
Use PgBouncer/CloudNativePG Pooler for high connection counts. Use transaction pooling for compatible 
stateless workloads. Use session/direct endpoints for operations requiring session affinity, session GUCs, 
temporary tables, LISTEN/NOTIFY, or administrative workflows.
27. Storage architecture
27.1 Live PostgreSQL storage
Use provider block/NVMe-backed storage for live database data where possible. PostgreSQL WAL and database 
files remain on the tenant instance's persistent volume. Object storage is not used as the live PostgreSQL 
storage layer.
27.2 Backup object storage
Backups and WAL archives use S3-compatible object storage: [Rev 3.2] Cloudflare R2 (bucket per cell,
prefix per tenant, bucket locks). Live data uses TopoLVM LVs on local NVMe [Rev 4.0]; HA plans replicate across nodes
(Phase 3). Original note: R2 is a low-cost option because it has no egress 
charges and is S3-compatible, but the exact Barman/R2 restore path must pass conformance tests.
27.3 Storage expansion
1. Validate entitlement.
2. Check cluster/node capacity and storage class.
3. Expand the PVC according to provider/storage support.
4. Wait for filesystem and PostgreSQL capacity to converge.
5. Verify database health and reported capacity.
6. Record the new entitlement and usage.
28. Future MySQL compatibility
Keep the control plane generic while V1 remains PostgreSQL-only. Generic concepts include database, cluster, 
credential, backup, restore, scale, replica, migration and usage. A future MySQL adapter should not require 
rebuilding billing, authentication, MCP policy or the customer dashboard.

The economic model is shared compute; the operational model is per-tenant PostgreSQL instances; the
